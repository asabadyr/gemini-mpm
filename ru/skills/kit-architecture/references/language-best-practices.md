# Лучшие практики для множества языков (Polyglot)

Комплексная матрица лучших практик для 12 технологических стеков (Polyglot), охватывающая идиоматичную модульность, ООП/трейты/композицию, обработку ошибок, параллелизм и канонические инструменты.

### 1. Python
- **Инструменты:** Используйте `uv` для быстрого разрешения зависимостей, `ruff` для линтинга/форматирования и `mypy` для строгой проверки типов.
- **Типы и ООП:** Отдавайте предпочтение `@dataclass(frozen=True, slots=True)` и Pydantic v2 для неизменяемых доменных моделей. Используйте `typing.Protocol` для duck-typed интерфейсов.
- **Архитектура:** Применяйте Constructor DI (Внедрение зависимостей через конструктор).
- **Параллелизм и ресурсы:** Используйте тайм-ауты `asyncio`, чтобы предотвратить зависание сопрограмм (coroutines). Строго управляйте ресурсами с помощью `@contextmanager`.

### 2. TypeScript / Node.js
- **Типы:** Используйте `unknown` + Zod для сужения типов на границах времени выполнения. Используйте размеченные объединения (discriminated unions) + `never` для исчерпывающих конструкций `switch`.
- **Архитектура:** Предпочтительно внедрение зависимостей через интерфейсы (Interface DI). Избегайте файлов `index.ts` типа "бочка" (barrel), чтобы предотвратить циклы круговых зависимостей.
- **Параллелизм:** Используйте `stream/promises` `pipeline` для обработки данных с эффективным использованием памяти. Полагайтесь на `AbortSignal.timeout` для отмены fetch/асинхронных операций.

### 3. Go
- **Типы и ООП:** Определяйте небольшие интерфейсы из 1-3 методов на стороне потребителя. Отдавайте предпочтение композиции перед наследованием.
- **Параллелизм:** Передавайте `context.Context` везде. Используйте `errgroup` для структурированного параллелизма.
- **Обработка ошибок:** Оборачивайте ошибки с помощью `%w` и проверяйте их с помощью `errors.Is`/`errors.As`.
- **Архитектура:** Организуйте код по доменным пакетам. Полностью избегайте функций `init()`. Всегда запускайте `go test -race`.

### 4. Rust
- **Память и типы:** Отдавайте предпочтение заимствованию (borrowing), а не `.clone()`. Используйте перечисления ADT (алгебраические типы данных) + трейты (traits) для моделирования конечных автоматов.
- **Обработка ошибок:** Используйте `thiserror` для ошибок библиотек и `anyhow` для приложений. Добивайтесь нулевого использования `.unwrap()` или `.expect()` в продакшене.
- **Параллелизм:** Используйте неблокирующие каналы `tokio` и async/await.
- **Инструменты:** Запускайте `cargo clippy -D warnings`, чтобы обеспечить соблюдение строгих идиом языка.

### 5. Java / Kotlin (JVM)
- **Типы:** Используйте Java `record` или Kotlin `data class` для неизменяемых DTO. Используйте `sealed` классы + сопоставление с образцом (pattern matching) для исчерпывающих доменных событий.
- **Архитектура:** Обеспечьте строгое разделение между доменными моделями и сущностями JPA. Используйте Constructor DI (Spring/Guice).
- **Параллелизм:** Отдавайте предпочтение виртуальным потокам (Virtual Threads - Project Loom) в Java 21+ или структурированному `CoroutineScope` в Kotlin.

### 6. C# / .NET
- **Типы:** Используйте первичные конструкторы (primary constructors), `record` или `readonly record struct` для неизменяемости. Включите ссылочные типы, допускающие значение null `<Nullable>enable</Nullable>`.
- **Параллелизм и ресурсы:** Передавайте `CancellationToken` от начала до конца. Используйте `await using` для асинхронно освобождаемых ресурсов (async disposables).
- **Данные:** Предотвращайте запросы N+1, используя EF Core `.AsNoTracking()` для проекций "только для чтения".

### 7. Frontend UI (React / Next.js / Vue / Svelte)
- **Компоненты:** Сохраняйте размер компонентов `<=150-200` строк кода. Извлекайте пользовательские хуки/композаблы (composables) для логики.
- **Состояние:** Отдавайте предпочтение производному состоянию (derived state), а не синхронизации через `useEffect`. Строго отделяйте состояние сервера (React Query/SWR) от состояния клиента (Zustand/Pinia).
- **Архитектура:** Отдавайте предпочтение композиции (передача `children`/`slots`), а не глубокому пробрасыванию пропсов (prop-drilling). Обеспечьте соблюдение стандартов семантической доступности `a11y`.

### 8. PHP (Modern 8.2+ / Symfony / Laravel)
- **Типы:** Всегда используйте `declare(strict_types=1)`. Используйте `readonly class` и типизированные `enum` (backed enums) для объектов-значений.
- **Архитектура:** Отдавайте предпочтение PSR-11 Constructor DI перед статическими фасадами в ядре домена. Используйте FormRequest/DTO для валидации на границах.
- **Данные:** Защищайтесь от запросов N+1 с помощью нетерпеливой загрузки (eager-loading) в Eloquent/Doctrine.
- **Инструменты:** Запускайте `phpstan --level=8` и тестируйте с помощью `pest` или `phpunit`.

### 9. Ruby (Ruby 3+ / Rails)
- **Архитектура:** Сохраняйте модели ActiveRecord размером `<200-300` строк кода, свободными от божественных коллбэков (god-callbacks). Извлекайте логику в простые объекты Ruby (Service/Query/Form/Policy объекты).
- **Типы:** Используйте `Data.define` для неизменяемых объектов-значений (value objects).
- **Данные:** Используйте `includes` и `strict_loading` для предотвращения запросов N+1.
- **Инструменты:** Обеспечьте соблюдение стиля и спецификаций с помощью `rubocop` и `rspec`.

### 10. Elixir / OTP (Phoenix)
- **Архитектура:** Создавайте функциональное ядро (functional core), обернутое в оболочку процесса OTP. Используйте границы контекста Phoenix (Phoenix Context boundaries), чтобы отделить бизнес-домены от веб-контроллеров/LiveViews.
- **Данные:** Используйте `Ecto.Multi` для явных транзакций базы данных.
- **Параллелизм:** Полагайтесь на деревья контроля (supervision trees). Используйте `GenServer` *только* для состояния времени выполнения и параллелизма — никогда не используйте его только для организации кода!
- **Инструменты:** Убедитесь, что `mix credo --strict && mix dialyzer && mix test` проходит успешно.

### 11. Swift / Dart (Mobile & Cross-Platform)
- **Типы и Архитектура:** Swift: Используйте протокольно-ориентированное программирование (Protocol-Oriented Programming) и типы значений `struct`. Dart: Используйте надежную null-безопасность (sound null-safety), неизменяемые состояния `sealed class` и однонаправленную архитектуру BLoC/Riverpod.
- **Параллелизм и память:** Swift: Используйте `async/await` структурированную отмену `Task` и изоляцию `@MainActor`. Используйте слабые ссылки `[weak self]` для защиты от циклов удержания (retain cycles).
- **Инструменты:** `swift test` / `flutter analyze && flutter test`.

### 12. C / C++ (Modern C++20/23 & Systems C)
- **Память:** Полагайтесь на детерминированное владение RAII. Используйте `std::unique_ptr`, `std::span` и `std::string_view`. Обеспечьте нулевое использование сырых владеющих `new`/`delete`.
- **Типы:** Агрессивно используйте `[[nodiscard]]`. Возвращайте `std::expected` или `std::optional` вместо сырых кодов ошибок.
- **Архитектура:** Следуйте правилу нуля/пяти (Rule of Zero/Five).
- **Инструменты:** Запускайте `clang-tidy` и компилируйте с `-fsanitize=address,undefined` (ASan/UBSan).

## Сквозные проблемы: Логирование, Метрики и Трассировка

Независимо от языкового стека, сквозные проблемы, такие как логирование и телеметрия, должны обрабатываться единообразно, не загрязняя доменную логику.
- **Структурированное логирование:** Выводите логи как структурированный JSON (например, `pino` в Node, `structlog` в Python, `slog` в Go). Включайте идентификаторы корреляции (correlation IDs) для отслеживания запросов через границы микросервисов.
- **Промежуточное ПО / Перехватчики (Middleware/Interceptors):** Внедряйте логирование, метрики и трассировку на границе транспорта (HTTP middleware, gRPC interceptors) или через декораторы, сохраняя ядро домена чистым.

## Управление зависимостями и инструменты CI/CD

Чистая архитектура требует строгого автоматизированного контроля.
- **Файлы блокировки (Lockfiles):** Всегда делайте коммит `package-lock.json`, `poetry.lock`, `Cargo.lock`, `go.sum` и т.д., чтобы обеспечить воспроизводимые сборки.
- **Автоматическое обновление зависимостей:** Используйте инструменты вроде Dependabot или Renovate, чтобы поддерживать актуальность библиотек, предотвращая накопление технического долга.
- **Непрерывная интеграция (CI):** Каждый PR должен запускать форматер, линтер, статический анализатор типов, модульные тесты и этап сборки. Если CI падает, PR не может быть объединен. Это не подлежащее обсуждению правило предотвращает деградацию архитектуры с течением времени.
