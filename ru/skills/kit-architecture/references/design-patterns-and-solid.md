# Шаблоны проектирования и принципы SOLID

## Основной принцип
**"Паттерны решают конкретные структурные проблемы (запахи кода); нет проблемы => нет паттерна."**

Перед применением любого шаблона выполните калибровку в соответствии с контекстом:
- **Production Mainline (Основная производственная линия)**: Требует строгой развязки, тестируемости и соблюдения SOLID.
- **Prototype/Scratch (Прототип/Черновик)**: Акцент на скорость; допускается незначительная связность, но избегайте глубоких антипаттернов.

## Таблица основ SOLID и ООП

| Принцип | Описание | Руководство по реализации |
| :--- | :--- | :--- |
| **SRP** (Единственная ответственность) | У класса должна быть только одна причина для изменения. | Отделяйте доменную логику от сохранения (persistence) и транспорта. |
| **OCP** (Открыт/Закрыт) | Открыт для расширения, закрыт для модификации. | Используйте интерфейсы/протоколы для добавления поведения без редактирования основных файлов. |
| **LSP** (Подстановка Барбары Лисков) | Подтипы должны быть взаимозаменяемыми с базовыми типами. | Избегайте выбрасывания `NotImplementedError` в подклассах. |
| **ISP** (Разделение интерфейса) | Клиенты не должны зависеть от методов, которые они не используют. | Отдавайте предпочтение небольшим, узконаправленным интерфейсам (например, 1-3 метода) перед толстыми. |
| **DIP** (Инверсия зависимостей) | Зависите от абстракций, а не от конкретизаций. | Внедряйте зависимости через Constructor DI; используйте порты и адаптеры. |

### Общие рекомендации по ООП
- **Композиция важнее наследования**: Сохраняйте глубину наследования `<=2`. Используйте композицию и интерфейсы для разделения поведения.
- **Constructor DI (Внедрение зависимостей через конструктор)**: Всегда внедряйте зависимости через конструктор для обеспечения тестируемости. Избегайте глобального состояния или одиночек (Singletons).
- **Неизменяемые граничные DTO**: Данные, пересекающие границы системы (сеть, база данных), должны отображаться в неизменяемые DTO/записи.

## Дерево принятия решений

Используйте это диагностическое дерево для сопоставления архитектурных запахов с соответствующими паттернами:

- **Нетестируемая сильная связность** ➔ **Constructor Dependency Injection (DI)**
- **Разрозненные бизнес-правила / Смешанные проблемы** ➔ **Service Layer (Доменный фасад)**
- **Протекание логики сохранения в домен** ➔ **Repository Pattern (Паттерн Репозиторий)**
- **Частые изменения сторонних библиотек / Изменения API** ➔ **Adapter / Anti-Corruption Layer (ACL)**
- **`3+` повторяющихся переключателей (switch) по тегу типа** ➔ **Strategy / Handler Registry (Стратегия / Реестр обработчиков)**
- **Сложное многовариантное создание объектов** ➔ **Factory / Builder (Фабрика / Строитель)**
- **Циклические вызовы `A->B->C->A`** ➔ **Domain Events / Mediator (Доменные события / Посредник)**
- **Каскадные задержки восходящих зависимостей** ➔ **Circuit Breaker / Bulkhead (Предохранитель / Переборка)**
- **Повторяющийся сквозной шаблонный код (логи, авторизация)** ➔ **Decorator / Middleware (Декоратор / Промежуточное ПО)**

## Диагностическая матрица "Запах кода -> Паттерн"

| Запах / Симптом | Диагноз | Рекомендуемый паттерн |
| :--- | :--- | :--- |
| Жестко закодированный `new Database()` внутри домена | Сильно связанный ввод/вывод (I/O) | Constructor DI + Repository |
| Толстый контроллер, обрабатывающий JSON и логику БД | Отсутствие границы | Service Layer + DTOs |
| Бесконечные `if/else` по типам пользователей | Отсутствие полиморфизма | Strategy Pattern |
| Проблемы из-за обновлений сторонних SDK | Домен заражен поставщиком | Anti-Corruption Layer |
| 10 параметров в конструкторе | Слишком много зависимостей | Builder или Facade |

## Антипаттерны / Красные флаги

Избегайте этих распространенных ловушек при попытке реализовать чистую архитектуру:

1. **Скрытые зависимости Service Locator**: Не передавайте `Container` или `Locator`. Это скрывает то, какие зависимости на самом деле нужны классу. Используйте явный Constructor DI.
2. **Анемичные обертки-пустышки**: Не создавайте репозитории или сервисы, которые просто перенаправляют вызовы 1:1 к ORM, не добавляя никакой доменной ценности. Если это прототип CRUD, просто используйте ORM.
3. **Преждевременные иерархии абстрактных фабрик**: Применение `AbstractWidgetFactory` в скрипте размером `<200` строк кода — это спекулятивный YAGNI. Делайте все просто, пока вариативность не станет действительно необходимой.
4. **Неправильное объединение (Wrong-DRY) кросс-доменной связности**: Не дедуплицируйте код, который просто *оказался* структурно похожим, если он принадлежит к разным бизнес-доменам (например, если у `User` и `Product` есть `name`). Позвольте им развиваться независимо.

## Глубокое погружение: Композиция важнее наследования

Одним из наиболее часто нарушаемых принципов в унаследованных (legacy) кодовых базах является чрезмерное использование наследования. Глубокие деревья наследования (глубина > 2) приводят к проблеме хрупкого базового класса (Fragile Base Class), когда изменение в базовом классе непреднамеренно ломает удаленные подклассы.

Чтобы смягчить это:
- **Отдавайте предпочтение интерфейсам/протоколам:** Определяйте, что объект *делает*, а не кем он *является*.
- **Используйте декораторы:** Если вам нужно добавить поведение классу, оберните его в декоратор, а не создавайте подкласс. Это позволяет комбинировать поведение во время выполнения.
- **Извлекайте стратегии:** Если подкласс существует только для переопределения определенного алгоритма, извлеките этот алгоритм в объект Strategy и внедрите его в базовый класс. Это мощный способ соблюсти принцип открытости/закрытости (OCP).

## Глубокое погружение: Правильное использование паттерна Репозиторий

Паттерн Репозиторий часто понимают неправильно, что приводит к созданию анемичных оберток вокруг ORM. Истинный репозиторий работает на уровне домена, имея дело исключительно с доменными моделями, а не со строками базы данных или Active Records.

- **Интерфейс в Домене, Реализация в Инфраструктуре:** Интерфейс репозитория должен быть определен на уровне Домена, чтобы инвертировать зависимость. Реализация живет на уровне Инфраструктуры.
- **Коллекционо-подобный интерфейс:** Методы должны напоминать коллекцию (например, `add`, `remove`, `findById`), абстрагируя тот факт, что за ней стоит база данных.
- **Отсутствие логики сохранения в домене:** Доменная модель не должна знать, как себя сохранить.

Строго применяя эти рекомендации, вы гарантируете создание тестируемой, слабосвязанной архитектуры, способной масштабироваться и адаптироваться к меняющимся требованиям с течением времени без необходимости переписывать всю систему с нуля.
