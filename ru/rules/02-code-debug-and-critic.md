# Инженерная гигиена, 5-фазная отладка и протокол критика (`02`)

## 1. Инженерные ограничения, модульность и архитектура (`🔴`)

### 1.1. Базовые принципы цепочки вызовов и ограничений
| Принцип | Исполнение |
|---|---|
| **Запрет побочных эффектов при импорте** | Импорт модуля на верхнем уровне **НИКОГДА НЕ ДОЛЖЕН** открывать сокеты БД/сети, запускать фоновые циклы/потоки, читать незащищённые секреты или менять диск/окружение |
| **Существующие артефакты — жёсткий контракт** | Имеющиеся тесты, фикстуры (`conftest.py`, seed-данные) и публичные схемы неприкосновенны: при падении тестов чини продакшен-код — **НИКОГДА** не ослабляй ассерты, не удаляй падающие тесты и не подменяй фикстуры, если спецификация явно не менялась |
| **Сквозной проход цепочки вызовов** | Проследить `Entrypoint -> Caller/Orchestrator -> Callee -> DB/External Side-Effect -> Return/Error Handling` от начала до конца перед написанием кода или одобрением фикса |
| **Контракты впереди реализации** | Зафиксировать предусловия, постусловия, инварианты и типы ошибок до написания тел функций (пропускать формальность только для хотфиксов `<=20` LOC вне авторизации и криптографии) |

### 1.2. Калибровка: Продуктовый Mainline vs Прототип/Scratch
| Контекст / Скоуп | Допустимая архитектура и ограничения |
|---|---|
| **Продуктовый Mainline**<br>*(ПО УМОЛЧАНИЮ, если неясно)* | `src/`, `app/`, `pkg/`, `internal/`, `lib/`, сервисы. Требует полных границ SOLID/OOP/DI, жёстких лимитов LOC и сложности, нулевого copy-paste дублирования, проверенных паттернов проектирования вместо ad-hoc ветвлений и полного аудита `code-critic`. |
| **Прототип / Scratch / Разовый скрипт** | `scratch/`, `scripts/oneoff*`, явно помеченные пользователем одноразовые PoC. Допускается единый связный файл (`<200-300` LOC) без спекулятивных фабрик/DI; **НИКОГДА** не должен импортироваться в mainline или мержиться без предварительной модуляризации. |

### 1.3. Жёсткая модульность, лимиты размера и сложности (Mainline)
| Масштаб | Лимиты и барьеры |
|---|---|
| **Файл** | Планировать модульное разделение на **`400` LOC**, жёсткий предел **`600` LOC** (запрет на God-файлы `600+` LOC). |
| **Класс / Структура / UI Компонент** | **`<=300` LOC** (`<=200` LOC для UI компонентов), строгое соблюдение единственной ответственности (`SRP`). |
| **Функция / Метод** | Целевой размер **`<=30` LOC**, жёсткий предел **`50` LOC**; Цикломатическая сложность **`<=10`**; Максимальная глубина вложенности **`<=3`** (требовать guard clauses / ранние возвраты вместо arrow-spaghetti). |

### 1.4. Search-Before-Create и DRY Дедупликация
| Принцип | Действие |
|---|---|
| **Сначала ищи & Одна реализация** | Искать существующие модули, хелперы и сервисы (grep) *до* написания нового кода; **Одна реализация на фичу** (немедленно удалять устаревший/мёртвый инлайн-код). |
| **Пороги консолидации (DRY)** | Извлекать переиспользуемые функции/коллабораторы, если **`2+` блока совпадают на `>80%`** в одном домене, если общая логика **`>=30` LOC** или структурное сходство между модулями **`>50%`**. |
| **Защита от ложного DRY** | Никогда не сливать разные бизнес-домены только из-за случайного сходства 5-строчной формы, и никогда не импортировать тестовые хелперы в продакшен-код. |

### 1.5. ООП, SOLID, Композиция и паттерны (Code-Smell -> Pattern)
Применять для решения конкретных "запахов", избегать спекулятивного YAGNI; сверяться с `/kit-architecture`.

| Запах кода / Структурный дефект | Требуемый паттерн / Архитектурный фикс |
|---|---|
| Глубокое наследование | **Композиция вместо наследования** (глубина наследования `<=2`; предпочитать интерфейсы/`Protocol`/traits + внедрённые коллабораторы). |
| Скрытые побочные эффекты / Глобальное состояние | **Внедрение зависимостей (DI) через конструктор/параметры** (запрет на инстанцирование конкретных клиентов БД/HTTP/SDK или мутацию глобального стейта внутри доменных классов). |
| `3+` повторения `if/elif`/`switch` по типу/статусу | **Стратегия (Strategy) / Полиморфный реестр обработчиков / Dispatch Map**. |
| Доменная логика завязана на SQL/ORM/NoSQL | **Репозиторий (Repository)**. |
| Модели внешних 3rd-party API/SDK протекают в домен | **Адаптер / Антикоррупционный слой (ACL)**. |
| Сложное создание объекта со множеством вариаций | **Фабрика (Factory) / Строитель (Builder)**. |
| Циклические зависимости сервисов (`A -> B -> C -> A`) | **Доменные события (Domain Events) / Pub-Sub**. |
| Каскадные сбои из-за медленных апстримов | **Circuit Breaker / Bulkhead + Таймаут**. |
| Сквозное логирование/кеширование/ретраи/auth | **Декоратор / Middleware** вместо скопипащенных обёрток. |

## 2. Шаблон промпта делегирования HSDF (`🟡`)
Структурируй задания субагентам компактными полями с точными путями и ошибками (никогда не сжимай пути к файлам, номера строк, имена инструментов и стектрейсы):
```yaml
tier: T1 | T2a | T2b | T3
role_profile: "<exact-model> (<Low|Medium|High>)" # опционально: профиль скоростной 5-ролевой матрицы (Разработчик/Тестировщик <fast-workhorse-model> (High), Ревьюер <frontier-model> (High))
Effort: Low | Medium | High
task: "<цель в одно предложение>"
scope_allowlist: ["exact/path/file1.ts", "exact/path/file1.test.ts"]
knowledge_refs: ["exact/path/to/GEMINI.md", ".agents/knowledge/00-INDEX.md", ".agents/knowledge/memories.md"]
read_anchors: ["exact/path/file1.ts:120-180 | ClassOrSymbol | callers/callees"] # опционально: якоря чтения от Explorer/Task Setter
contracts: ["<предусловия/постусловия, инварианты, неприкосновенные ограничения>"]
observable: "<точная команда / HTTP / БД / файловый вывод, доказывающий поведение в рантайме>"
return: ["git diff --stat", "дословный stdout lint/typecheck/test", "доказательство observable"]
context: |
  <краткая вводная, ссылки на .agents/knowledge/, сырые логи ошибок>
```

## 3. Систематический 5-фазный шлюз отладки (`🔴`)
Никаких угадываний и слепых патчей. Проходи все 5 фаз строго по порядку:
| Фаза | Обязательное действие | Запрещённый анти-паттерн |
|---|---|---|
| **1. Воспроизведение (Reproduce)** | Детерминированно вызвать сбой по требованию и зафиксировать дословную ошибку/состояние | Менять код до получения воспроизводимого отказа |
| **2. Изоляция (Isolate)** | Сузить границу сбоя через `git bisect`, минимальный входной пример или бинарный поиск по слоям | Менять несколько переменных одновременно |
| **3. Первопричина (Root Cause)** | Проследить испорченное значение/состояние вверх по цепочке вызовов до точки нарушения инварианта | Останавливаться на строке падения вместо места входа некорректного состояния |
| **4. Устранение причины (Fix Cause)** | Починить нарушенный инвариант в источнике и проверить всех вызывающих абонентов в цепочке | Маскировка симптомов через `try/catch`, подстановка дефолтов поверх битого состояния, произвольные `sleep` или слепые ретраи |
| **5. Регрессионный тест (Regression Test)** | Добавить детерминированный тест, который **падает без фикса** и проходит с фиксом | Закрывать багфикс без регрессионного покрытия |

## 4. Протокол контекстно-изолированного критика (`code-critic`) (`🔴`)
- **Изоляция от эффекта якорения**: Вызывай `code-critic` (или независимого Checker на `pro`/`inherit`), передавая **ТОЛЬКО**:
  1. Исходное требование пользователя и критерии приёмки,
  2. Интерфейсные контракты и схемы данных,
  3. `git diff` / `git status -s` и затронутые файлы,
  4. Дословный вывод линтера, проверки типов и тестов,
  5. Точный **рантайм-observable** для проверки.
  **ВЫРЕЗАЙ** оправдания Maker-субагента, его рассказ о том, «почему сделано так», и текст коммит-месседжей, чтобы Критик оценивал факты без предвзятости.
- **Протокол чтения при аудите (`🟡`)**: `code-critic` соблюдает `Read-Once` (без повторных чтений неизменённого файла) и `Grep-Before-Read` (>400 строк). Критик **ОБЯЗАН** прослеживать реальные цепочки вызовов (`import`, базовые классы, вызывающие и вызываемые методы) через границы модулей на нужную глубину, не ограничиваясь поверхностным просмотром диффа.
- **Фильтр уверенности и матрица вердиктов**:
  - Репортить **только** находки с уверенностью **`>=80%`** (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`).
  - **Любая находка `CRITICAL` или `HIGH`** (корректность, целостность цепочки вызовов, архитектура/DRY/модульность, конкурентность, качество тестов, чистота грязного Git-дерева или безопасность) => **обязательный `VERDICT: BLOCK`** → направлять локальные механические исправления через тёплый `send_message` (`WARM_FIX`), а при архитектурных/инвариантных сбоях или неудачном первом ретрае выполнять **Promote-on-Review** (`PROMOTE_MAKER` — Разработчик/Тестировщик `<fast-workhorse-model> (High)` повышается до `<frontier-model> (High)`, все ревьюеры строго на `<frontier-model> (High)`):
    * в контуре **`teamwork`**: оркестратор спавнит `iterN+1` воркера, повышенного до `<frontier-model> (High)`, с чистым `DISPATCH.md`;
    * в нативном **`swarm`**: `swarm{action:"model"}` переключает воркера на `<frontier-model> (High)` на месте либо вызывается свежий `swarm{action:"add"}` для сброса контекста;
    * в резервном **`invoke_subagent`**: свежий вызов `invoke_subagent(Model="pro", Effort="High")` без рассуждений предыдущего Maker согласно `01-orchestration.md` §2.2.
  - **Только `MEDIUM` / `LOW`** => `VERDICT: WARN` (или `APPROVE`, если замечаний нет).
- **Обязательные триггеры эскалации безопасности (OWASP + Multi-Tenant)**:
  Любой дифф, затрагивающий **auth/JWT/сессии**, **криптографию и ключи**, **сборку SQL/NoSQL-запросов**, **вызов shell/subprocess**, **файловые пути и загрузки**, **десериализацию** или **границы изоляции тенантов**, автоматически включает обязательный аудит на инъекции, обход авторизации, утечку секретов и межтенантную утечку данных внутри ревью Checker (`CRITICAL`/`HIGH` => `BLOCK`).
