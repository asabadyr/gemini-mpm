# Протокол оркестрации и субагентов (`01`)

## 1. Лестница эскалации выполнения
| Уровень задачи | Признаки | Режим выполнения |
|---|---|---|
| **Прямой (Inline)** | Проверка статуса, вопросы по архитектуре, чтение `<=3` файлов, тривиальная правка `<20` LOC в 1 шаг | Выполнить напрямую в **Main Agent** (ноль накладных расходов на холодный старт субагентов) |
| **Стандартный многошаговый** | Многофайловое исследование, фикс бага, фича (`20–500` LOC), написание и прогон тестов | Делегировать асинхронно связке **Maker + Checker** (`invoke_subagent`); кратко озвучить план субагентов и **сразу завершить ход**, чтобы Main Agent оставался отзывчивым в чате |
| **Сложный / Кампания** | `>500` LOC, редизайн межсервисных контрактов/схем/авторизации, неочевидные компромиссы или долгий автономный прогон | Рекомендовать `/plan` или `/grill-me` для выравнивания на берегу; рекомендовать `/boost`, `/teamwork` или `/goal` для глубокой многоагентной/автономной работы (и `/compact` или `/kit-handoff pause` при росте контекста) |

## 2. Обязательная связка Maker–Checker и маршрутизация `Model` + `Effort` (`🟡`)
Любой нетривиальный цикл исследования, разработки или тестирования требует **минимум 2 субагентов**: **Maker** (исследует, пишет код, гоняет тесты) + **Checker** (независимый антагонистический `code-critic` или ревьюер на `pro`/`inherit`, проверяющий дифф, цепочки вызовов, граничные случаи, качество тестов и соблюдение правил). Явно задавай `Model` и заголовок `Effort:` при каждом вызове `invoke_subagent`:

| Архетип субагента | Параметр `Model` | Заголовок промпта | Целевая нагрузка |
|---|---|---|---|
| **Механический / Инвентаризация** | `flash_lite` | `Effort: Low` | Поиск файлов/символов, фильтрация логов, сверка версий/конфигов, узкие точечные справки |
| **Целевой исполнитель (Maker)** | `flash` | `Effort: Medium` | Локализованный ресёрч кода, чётко специфицированная реализация, написание и запуск юнит-тестов |
| **Глубокий анализ / Критик** | `pro` (или `inherit`) | `Effort: High` | Форензика первопричин, диффы конкурентности/протоколов/безопасности, **Adversarial Checker (`code-critic`)** |

## 3. Волновой параллелизм и проверка `<workspace>/.git` (`🔴`)
- **Строго волновая диспетчеризация**:
  1. **Wave 0**: Зафиксировать общие типы, схемы данных и контракты вызовов.
  2. **Wave 1**: Запустить параллельных Maker-субагентов со **строго непересекающимися списками разрешённых файлов (`scope_allowlist`)** (запрещено распараллеливать связанные баги или пересекающиеся файлы в одном рабочем дереве).
  3. **Wave 2**: Интегрировать изменения, прогнать полный набор тестов и вызвать Checker.
- **Проверка `<workspace>/.git` перед изоляцией worktree**: Обязательно проверь наличие `<workspace>/.git` **до** передачи `Workspace="share"` или `"branch"` в `invoke_subagent`.
  - **Фоллбэк для зонтичных папок без корневого `.git`**: Мультирепо-каталоги без корневого `.git` падают при `Workspace="share"|"branch"`. Используй `Workspace="inherit"` с непересекающимся владением подрепозиториями либо создавай worktree явно через `git -C <subrepo> worktree add`.
  - **Промежуточные `wip:`-коммиты**: Разрешены **исключительно** внутри проверенных изолированных `Workspace="share"|"branch"` или выделенных git worktree для сохранения прогресса песочницы; строго запрещены в общем грязном дереве без запроса пользователя.

## 4. Батчинг, шлюз Stage 3.5 и тёплое vs свежее делегирование
| Механизм | Правило |
|---|---|
| **Сначала контекст проекта** | Прочитать `.agents/knowledge/00-INDEX.md` и `.agents/knowledge/memories.md` (если существуют) до запуска широкого поиска по кодовой базе |
| **Связный батчинг** | Объединять `реализация + lint + typecheck + тесты + сырой вывод` в `5–7` крупных делегирований за сессию вместо `20+` микро-вызовов |
| **Шлюз Stage 3.5** | Maker **ОБЯЗАН** пройти сборку, линтер, проверку типов и релевантные тесты до того, как Main Agent вызовет Checker |
| **Тёплый `send_message`** | Использовать `send_message(Recipient=conversationId)` **только** для доработок в том же скоупе или уточняющих вопросов (без перезагрузки контекста) |
| **Свежий `invoke_subagent`** | Создавать нового субагента при расширении скоупа или смене роли (`Research -> Maker` или `Maker -> Context-Isolated Critic`) |
| **Финальная приёмка в Main Agent** | Итоговую приёмку всегда держит Main Agent; при вердикте `BLOCK` от Checker или непроверенных допущениях отправлять правки обратно в Maker через `send_message` до отчёта пользователю |
