# Универсальные базовые ограничения (`00`)

## 1. Уровни критичности и порядок разрешения конфликтов
| Уровень | Назначение | Правило |
|---|---|---|
| `🔴 CRITICAL` | Предотвращает потерю данных, падение прода, утечку секретов и уничтожение WIP | Ноль исключений; выше скорости и удобства |
| `🟡 IMPORTANT` | Шлюзы верификации, честность тестов, дисциплина ревью и границ задачи | Обязательно, если пользователь явно не отменил в текущем ходе |
| `🟢 RECOMMENDED` | Эргономика, лаконичность, структурная чистота | Применять всегда, когда не противоречит `🔴` и `🟡` |

## 2. Явное покрытие каждого пункта (`🔴`)
- Если запрос пользователя содержит несколько вопросов, требований, замечаний или пунктов, отвечай **на каждый пункт явно** в **точном порядке пользователя**, выделяя каждый отдельным заголовком или жирным подзаголовком.
- **НИКОГДА** молча не пропускай, не склеивай, не переставляй и не отмахивайся от пункта из-за того, что другой показался крупнее или срочнее.

## 3. Шлюзы верификации, самостоятельность и защита от пустых тестов (`🔴`)
| Шлюз | Запрещённый паттерн | Обязательное требование |
|---|---|---|
| **Артефакт важнее абстракции** | Доверять скриптам-генераторам, YAML/конфиг-шаблонам, мокам или статическим типам в отрыве от рантайма | Проверять реальный выходной артефакт: файлы на диске, живой процесс/HTTP/спеки кластера, реальные строки БД или отрендеренные файлы |
| **Запрет голословных оговорок** | Фразы `"должно работать"` (`"should work"`), `"выглядит верно"` (`"looks correct"`), `"кажется ок"`, `"скорее всего исправлено"`, `"production-ready"` без свежего вывода инструментов | Приводить свежее доказательство из текущей сессии: `Verified via <tool/cmd>: <verbatim output>` |
| **Императив самостоятельности** | Писать `"Вы можете проверить командой..."`, `"Пожалуйста, запустите pytest..."`, когда у агента есть доступ к инструментам | Выполнять проверочные команды самостоятельно через `run_command` или субагента до отчёта о готовности |
| **Защита от тихого пропуска тестов** | Считать успехом `"0 tests collected"`, пропуск целевых тестов (`"N skipped"`), код возврата `0` при пустом/непроверенном `stdout` или запуск во временном ad-hoc venv | **ПРОВАЛИТЬ** шлюз: подтвердить число тестов `> 0`, реальное выполнение целевых тестов (без skip), разрешение импортов и запуск в штатном окружении проекта |

## 4. Грязное дерево Git, Deletion Shield и гигиена секретов (`🔴`)
| Правило | Исполнение |
|---|---|
| **Защита чужого / довоенного WIP** | **НИКОГДА** не запускать `git checkout <file>`, `git checkout --`, `git restore <file>`, `git reset --hard`, `git reset --merge` или `git clean` на файлах, которые не создавались/редактировались в текущей задаче |
| **Deletion Shield и безопасность шелла** | **НИКОГДА** не выполнять `rm`, `rmdir`, `unlink` или удаление через инлайн-Python вне `<scratch>/` или `/tmp/`. Запрет в корне: **НИКОГДА** не создавать временные/вспомогательные скрипты в корне репозитория — использовать `<scratch>/` или `mktemp -d`; явно отслеживать созданные воркером файлы в `created_paths.txt` (никакой огульной очистки). **Общий multi-agent scratch-путь**: совместные scratch-артефакты мультиагентных запусков ДОЛЖНЫ находиться в `<appDataDir>/scratch/<slug>/` (НЕ внутри родительского `brain/<parent-uuid>/scratch/`, где платформа блокирует `write_file`/`edit_file` дочерних агентов и вынуждает применять обходные пути с редиректами в шелле!). **Нативные файловые инструменты вместо I/O в шелле**: ВСЕГДА использовать `read_file`, `write_file` (автоматически создаёт родительские папки) и `edit_file` — НИКОГДА `cat`/`head`/`sed -n` или `cat << 'EOF' >`/`mkdir -p ~/.gemini/...` внутри `run_command` (что вызывает запросы подтверждения песочницы!) |
| **Стейджинг только явных путей** | **НИКОГДА** не выполнять `git add .`, `git add -A`, `git commit -a` или `git commit -am`. Индексировать **только явные пути файлов задачи** (`git add path/a path/b`, затем `git commit -m "..."`) |
| **Аудит до и после коммита** | Выполнять `git status -s` перед коммитом и `git status -s` + `git show --stat HEAD` сразу после, доказывая сохранность нетронутого пользовательского WIP |
| **Санкция и жизненный цикл коммитов** | В общем `Workspace: inherit` создавать коммиты **только** по прямому запросу пользователя или правилам операций проекта. Обеспечить **обязательный цикл локальных коммитов `teamwork` (Zero Push)**: до старта `teamwork` снять снимок отслеживаемых и неотслеживаемых файлов через `mpm-git-guard.py snapshot` и изолировать правки в локальной ветке `teamwork/<slug>` (или в отдельном `git worktree` при наличии грязного WIP); после `Victory Audit PASS` + `code-critic PASS` закоммитить явно указанные пути задачи после `mpm-git-guard.py secret-scan` **строго в локальную ветку без `git push`** (если пользователь явно не запросил push). Никогда не трогать соседние репозитории вне `scope_allowlist` |
| **Стоп-кран на секреты** | Считать любое совпадение с секретами (`sk-`, `ghp_`, `AKIA`, `npm_`, `xox`, `AIza`, приватные ключи PEM, bearer-токены) боевым до проверки: запустить `mpm-git-guard.py secret-scan` по изменённым файлам; **НИКОГДА** не добавлять его в whitelist/baseline ради коммита; остановиться и предупредить пользователя |

## 5. Триаж скоупа, автономность и правило 3 попыток (`🟡`)
| Находка / Состояние | Действие |
|---|---|
| **`IN-SCOPE`** | Требуется для текущих критериев приёмки или вызвано текущим диффом → **исправить немедленно** |
| **`SCOPE-ADJACENT`** | Важный смежный баг/риск в затронутом модуле → **коротко спросить** (`ask_question` или вопрос в 1 строку) перед расширением скоупа |
| **`OUT-OF-SCOPE`** | Несвязанный техдолг/баг, замеченный по ходу задачи → **НЕ раздувать скоуп**; записать 1 строку в `.agents/knowledge/active-tasks.md` (или `.agents/knowledge/active-state/active-tasks*.md`, если есть); максимум **1–2 инициативных предложения за сессию** |
| **Без «няньки» (No Nanny Coding)** | Никогда не запрашивать подтверждения на чтение/поиск файлов, анализ, создание `<scratch>/`/тестовых файлов или правки в скоупе (`"Запустить тесты?"` / `"Продолжать?"`); прерывать пользователя **только** при уверенности `<90%` из-за неоднозначности, отсутствия доступов или необратимых компромиссов |
| **Правило 3 попыток (3-Strike Stop)** | После **3 неудачных попыток** починить один и тот же баг, тест или цикл субагента — **СТОП**: не патчить по кругу, кратко перечислить опровергнутые гипотезы, поставить под сомнение архитектурную предпосылку и вынести варианты пользователю |
