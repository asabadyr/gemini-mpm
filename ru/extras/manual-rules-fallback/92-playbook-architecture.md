# Плейбук для ручного использования (Резервный вариант): Архитектура (`92-playbook-architecture`)

Этот плейбук представляет собой ручной контрольный список (чек-лист) для обеспечения соблюдения принципов чистой архитектуры и безопасного поэтапного рефакторинга в случаях, когда автоматическое прогрессивное раскрытие информации отключено или не используется.

## 1. Пороги быстрого аудита (`audit`)
Если файл или модуль пересекает эти пороговые значения, он требует немедленной декомпозиции:
- **Файлы:** `> 400` (или `600`) строк кода (LOC).
- **Классы:** `> 300` строк кода.
- **Функции:** `> 50` строк кода.
- **Сложность:** Глубокая вложенность `> 3` или цикломатическая сложность `> 10`.
- **Дублирование:** `> 80%` идентичного кода в том же домене.
- **Антипаттерны:** Циклические импорты или конкретный ввод/вывод (I/O) внутри чистых доменных классов.

## 2. Протокол безопасного рефакторинга (`refactor`)
Никогда не делайте рефакторинг без страховки. Применяйте следующие ограничения:
- **Сначала тесты:** Убедитесь, что существующие тесты или характеризационные тесты проходят успешно (зеленые) ПЕРЕД тем, как прикасаться к коду.
- **Поэтапные шаги:** Перемещайте максимум `<= 200` строк кода за один шаг рефакторинга.
- **Немедленная проверка:** Запускайте набор тестов после каждой отдельной части. Откатывайте изменения, если тесты краснеют.
- **Одна реализация:** Удаляйте старые реализации; не оставляйте мертвый код или параллельные пути.
- **Расчет чистых строк (Net LOC):** Отслеживайте добавленные (`Added`), удаленные (`Removed`) и чистые (`Net`) строки кода.

## 3. Матрица выбора паттернов (`patterns`)
Применяйте паттерн только в том случае, если существует конкретная структурная проблема (запах):
- **Сильная связность (Tight Coupling) ->** Constructor Dependency Injection (Внедрение зависимостей через конструктор).
- **Разрозненная доменная логика ->** Service Layer (Сервисный слой / Фасад).
- **Протекание базы данных ->** Repository Pattern (Паттерн Репозиторий).
- **Частые изменения внешнего API ->** Anti-Corruption Layer (Антикоррупционный слой / Адаптер).
- **Бесконечные операторы Switch ->** Strategy / Handler Registry (Стратегия / Реестр обработчиков).
- **Циклические зависимости `A->B->C->A` ->** Domain Events / Mediator (Доменные события / Посредник).

## 4. Универсальные многоязычные правила (`lang`)
Независимо от технологического стека:
- **Зависимости:** Внедряйте зависимости (Constructor DI / Interface DI).
- **Неизменяемость:** Отображайте границы в неизменяемые DTO (например, `readonly`, `frozen`, `record`, `dataclass`).
- **Защита от N+1:** Всегда используйте нетерпеливую загрузку (eager-load) или загрузчики данных (dataloaders) в ORM.
- **Параллелизм:** Передавайте токены отмены/контексты от начала до конца; никогда не оставляйте зависшие промисы (promises) или подпрограммы.
- **Линтинг:** Поддерживайте отсутствие предупреждений (zero warnings) в нативном линтере/компиляторе (`ruff`, `clippy`, `tsc`, `phpstan` и т.д.).

## 5. Эскалация и проверки (Reviews)
Если ручной рефакторинг превышает стандартные лимиты (например, рефакторинг переплетенного унаследованного файла размером более 5000 строк кода с нулевым покрытием тестами), инициируйте ручную эскалацию:
- Не пытайтесь проводить рефакторинг без предварительного написания характеризационных тестов.
- Обсудите запланированные абстракции со старшим инженером или экспертом в предметной области.
- Сохраняйте Pull Requests (PR) небольшими и сфокусированными. PR должен строго содержать только изменения рефакторинга без добавления новых функций. Смешивание рефакторинга и работы над функциями в одном PR скрывает намерения и резко увеличивает риск регрессий. Ревьюеры должны иметь возможность сосредоточиться исключительно на структурной эквивалентности. Выполнение этого правила является критически важным для долгосрочного здоровья кодовой базы.
